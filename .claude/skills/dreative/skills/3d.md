# 3D

Use 3D only when spatial behavior improves meaning, demonstration, or product
understanding. A subject that is fully explained by a good photograph does not
need a renderer.

## Where the object comes from

Decide this before choosing a runtime. The order is not a preference, it is a
difficulty ranking — each step down is more work and more likely to look wrong.

1. **A licensed or CC0 model.** Poly Haven, Sketchfab's downloadable CC licences,
   or a supplied asset. See `../references/MEDIA_SOURCES.md`. For a realistic
   physical subject this is almost always the right answer and almost never the
   one that gets chosen.
2. **A photograph, used as a photograph.** If the object only needs to be seen
   rather than turned, 3D is the wrong tool. A well-cropped image beats a
   mediocre render every time.
3. **Modelled or reconstructed geometry.** Legitimate for schematics, data
   objects, abstract forms, and anything that is not pretending to be a
   photograph.
4. **Procedural DOM/CSS/SVG built to look dimensional.** This is entry 10 in
   `../exemplars/SLOP.md`. It is a valid stylistic choice and an invalid
   substitute for a real object. If it is meant to read as a real thing and does
   not, it has failed regardless of how much markup it took.

Photo-to-3D reconstruction is not an available capability. Photogrammetry needs
many controlled captures you do not have, and image-to-3D services return
unreliable geometry on exactly the detailed subjects that matter. Treat it as a
capability gap to raise with the user, never as something to attempt quietly.

## Lighting and material are the work

An unlit glTF on a gradient is the 3D equivalent of a stock hero. The renderer
is not what makes a render good, and this is where a technically working 3D
scene still looks worse than the flat design it replaced.

- Light it deliberately. A CC0 HDRI (Poly Haven) with a considered exposure
  beats three point lights every time. The environment is doing most of the job.
- Sample the palette from the real material, not from the page's accent colour.
  Reviewers notice invented colour before they notice geometry — *"the colour
  choice is weird for props"* is a lighting and material note, not a modelling
  one.
- Give the object a ground relationship. Contact shadow, reflection, or a
  surface. Floating objects with no shadow are the clearest tell of a scene
  nobody art-directed.
- Check scale and silhouette at 390px. A subject that reads at 1440px often
  becomes an ambiguous blob on a phone.

## Prefer the pre-rendered view

For a realistic physical prop that the user does not manipulate, render offline
and ship frames. It is cheaper at runtime, far more reliable on mobile, and much
harder to get visibly wrong, because the output is fixed at author time where it
can be inspected instead of at run time where it cannot.

- A turntable or process sequence scrubbed on scroll, built with the FFmpeg
  recipe in `../references/ASSET_PIPELINES.md`.
- A small set of authored views crossfaded between states.
- A single well-lit still, when the object only needs to be seen.

Reserve live WebGL for cases where the user genuinely moves the object, changes
its configuration, or needs a viewpoint the author cannot predict. That is a real
requirement and it is rarer than it feels while planning.

## Naming what shipped

Name the spatial contribution honestly: model, layered billboard, media plane,
procedural geometry, frame sequence, or pre-rendered view. A textured plane is
not a model, and a stepped image sequence is not continuous subject motion.

Browser checks confirm a canvas exists, is visible, is large enough, and changes
state. None of that can tell whether the object reads as the thing it is meant to
be. That judgement is the user's, so show the render and ask — do not report a
passing smoke run as evidence the prop looks right.

## Runtime discipline

Cap DPR, lazy load, suspend offscreen, handle resize and context-loss failure,
and dispose every geometry, material, texture, and renderer. Provide a
lightweight fallback and an authored mobile form; the fallback must preserve the
product view or explanation, not degrade to a generic gradient.

Reject generic particles, floating decorative objects, invisible complexity, and
persistent canvases that cover copy or controls. Read
`../references/CREATIVE_EXECUTION.md`, `../systems/NATIVE_FOUNDATIONS.md`,
`../references/MEDIA_SOURCES.md`, and `../references/ASSET_PIPELINES.md`.
